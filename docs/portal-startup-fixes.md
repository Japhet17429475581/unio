# Исправления запуска, логов и заявлений — 23.10.2026

Версия клиента: `1.0.0-beta.3+4`.

## Что изменено

- Загрузочный Flutter-экран теперь сразу использует тёмную тему. Раньше его фон
  был тёмным, но системная панель получала светлый цвет из темы до восстановления
  настроек. Начальный стиль Flutter и четыре Android Launch/NormalTheme согласованы
  с фоном загрузки `#0B0D18`; белая подложка окна тоже убрана.
- Логи backend по умолчанию снова уровня INFO и идут в stdout немедленно.
  HTTP-запись содержит шаблон маршрута, метод, статус, время и сгенерированный
  request_id. Ошибки содержат тип, SQLSTATE при наличии и файл/строку/функцию.
  URL-параметры, IP, тело, заголовки, локальные переменные и текст исключения
  не записываются. Обычный `uvicorn.access` заменён безопасным middleware.
- Парсер заявлений поддерживает дополнительные category-select и ссылки edit без
  старой обёртки, явное пустое состояние без `.list-view`, logout-ссылку вместо
  logout-формы. Чужие страницы и login/challenge не считаются пустым списком.
  Без исходного HTML конкретного тестера это не подтверждение поддержки всей
  новой разметки портала.
- APK продолжает входить в портал напрямую. При ошибке чтения списка он может
  отправить в UNIO только код, платформу, версию и HTTP-статус. Endpoint требует
  токен UNIO, запрещает произвольные поля и ограничен шестью сообщениями в минуту
  на пользователя; клиент ограничивает повторы одного кода раз в минуту.
  Сами заявления, логин, пароль и HTML этим endpoint не принимаются.

## Какие файлы обновить на backend

Из `lib/backend/`:

```
main.py
privacy.py
server_logging.py        # новый
diagnostics.py           # новый
auth_api/auth.py
web_portal.py
web_push.py
redis_db.py
rate_limit.py
legal_versions.json
legal_versions_history.json  # новый
database/connection.py
migrations/001_privacy.sql
migrations/002_web_portal.sql
migrations/003_web_push.sql
Dockerfile
requirements.txt
```

`build/UNIO-BACKEND-beta.3-compatible.zip` содержит эти файлы и эту инструкцию.
`build/UNIO-BACKEND-beta.3-patch.zip` обновлён тем же совместимым содержимым.
Это дополнение к текущему backend проекта, не отдельная полная установка.
Новых миграций именно для совместимости нет. В архив включены существующие
001–003: `init_db` применяет их при запуске. Они создают недостающие таблицы
согласий/web-сессий/Web Push и индексы, не удаляя существующие аккаунты.
Это нужно в том числе для logout: он очищает связанные web-таблицы.
Если PWA пока не настраивается, ключи/origins не нужны для обычной работы APK.
Для самой PWA её настройка по `docs/pwa.md` остаётся обязательной.

### Совместимость с beta.1

Проверены обе доступные APK beta.1 (основная и fixes): они содержат документы
`1.1-draft-*`. Дополнительно сохранена предыдущая редакция `1.1-2026-10-21-*`
из доступных исходников. Текущая beta.2/beta.3 использует `1.2-2026-10-22-*`.
Хеши старых документов сверены с их текстами локально, без вывода содержимого.

`auth/guest` и `auth/consents` принимают только известные точные пары версия+SHA-256
из текущего реестра и истории. Старое согласие сохраняется со своей настоящей
версией: оно не считается принятием новой редакции. Произвольные версии,
подменённые хеши, отсутствие обязательных согласий и отозванные согласия отвергаются.
Новый вход в web-посредник по-прежнему требует актуальные документы, поскольку
там отличается обработка данных.

Контракты guest/me/logout, заголовок `X-Unio-Token`, формат/хеш токена и адреса API
сохранены. Обновление не сбрасывает токены beta.1 и не требует принудительного выхода.
Обычное истечение срока токена остаётся в силе. Отдельные тесты проверяют старый
guest-вход, синхронизацию согласий, me и logout.

Заменить весь набор с сохранением путей одним обновлением, установить зависимости
и только затем перезапустить сервис. БД, `.env`, адрес API и существующие ключи
не заменять. При обычном перезапуске одного экземпляра возможен короткий перерыв.
Совместимость со старым клиентом не исправляет его локальный HTML-парсер заявлений
и цвет панели: эти исправления появятся у пользователя после обновления APK.

Перезапустить/пересобрать backend на Bothost. Оставить `UNIO_LOG_LEVEL=INFO`
или не задавать переменную — это значение по умолчанию. Если поставить WARNING,
успешные HTTP-запросы снова исчезнут из логов. Dockerfile включает
`PYTHONUNBUFFERED=1`; при запуске вне контейнера можно использовать `python -u main.py`.
Не подключать поверх кода сырой access-log с query/headers/body. Срок хранения
и доступ к журналам задаются отдельно в панели хостинга.

Проверка после выкладки: открыть `/health`; должна появиться JSON-строка
с `event=http_request`, `route=/health`, `status=200` (или 503 при проблеме зависимостей).

При открытии заявлений в обновлённом клиенте:

- `portal_upstream_response` — ответ университета для PWA: операция и HTTP-статус.
- `portal_client_failure` — ошибка чтения списка на APK/PWA, код и версия клиента.
- `requests_empty_response` — пустое тело ответа.
- `requests_unrecognized_page` / REQ_PAGE — страница не распознана.
- `requests_access_challenge` / REQ_ACCESS — страница блокировки/проверки браузера.
- `portal_session_expired` — вместо данных получена форма входа.
- `portal_http_error` / `portal_network_error` — транспортная ошибка.

Отсутствие диагностического сообщения не доказывает отсутствие ошибки: отправка
best effort, может не дойти при отсутствии сети, истёкшем токене или старом backend.

## Клиенты и оставшаяся проверка

Установить новый APK поверх предыдущего. PWA обновить архивом на том же домене,
сохранив proxy и env. Серверная выкладка сама по себе не обновляет парсер в APK/PWA.

Проверены 39 Flutter-тестов и 51 backend-тест на синтетических данных
(включая совместимость beta.1);
статический анализ изменённых Dart-файлов прошёл без замечаний. Собраны APK и PWA
beta.3. В Chrome проверены вход, список заявлений, сохранение входа, удаление,
офлайн-перезапуск и обновление service worker; ошибок страницы и внешних запросов нет.
Браузерные API были подменены тестовыми ответами. Запросов
к персональной странице тестера и production БД не выполнялось. На физическом
телефоне нужно проверить холодный запуск с трёхкнопочной и жестовой навигацией.
Для окончательного подтверждения новой HTML-схемы нужен обезличенный HTML именно
страницы списка заявлений, которая открывается у тестера в браузере; не нужны
пароли, cookie, содержимое вложений или учётные данные.
